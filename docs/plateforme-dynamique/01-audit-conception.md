### Écarts et conception retenue

1. **Conserver les contrats et le moteur PREP.** Garder codes, formes des programmes/modules, blocs, traductions, `publicExercise`, validateurs et composants actuels. Extraire les contrôles réutilisables du générateur sans exécuter de JavaScript fourni par un administrateur. Le contenu éditable sera du JSON validé ; nouveaux types de blocs/exercices, fonctionnalités natives et permissions exigent toujours une version de l’application.
2. **Ajouter une source éditoriale Mongo derrière `contentService`.** Deux collections proposées : `PrepContent` (`kind=programme|module`, `code`, `revision`, `schemaVersion`, `status=draft|published|archived`, `payload`, auteurs/dates/hash) et `PrepPublication` (génération, manifeste de références aux révisions publiées, retraits et version minimale de schéma). Leçons et exercices restent imbriqués dans le module, comme aujourd’hui ; pas de modèle parallèle pour chaque bloc. Index unique `(kind, code, revision)`, index de liste `(kind, status, updatedAt, _id)` ; registre de publication actif unique. Les révisions publiées sont immuables.
3. **Publier atomiquement.** Écrire les révisions validées, puis basculer le manifeste par comparaison de génération ; une erreur laisse l’ancienne publication active. Cette bascule sur un document fonctionne aussi sur Mongo local sans replica set. Valider les références et codes de toutes les branches touchées avant activation. Pas de visibilité d’un brouillon ni de mélange ancien programme/nouveau module. Remplacer le cache éternel par snapshots de génération ; vérifier le registre avant de servir une nouvelle version, réutiliser ensuite les données immuables. Les scripts vidéo reçoivent un snapshot explicite ; pas de seconde source vivante en concurrence avec Mongo.
4. **Importer sans recréer les identifiants.** Migration explicite, idempotente, avec contrôle à blanc : importer les 8 programmes/39 modules, résoudre et enregistrer `organismeId/parcoursTypeId` plutôt que dépendre durablement des regex. Conserver le pack comme source de migration et catalogue de secours minimal. Ne jamais réimporter automatiquement au démarrage ni réécraser une édition admin. Les codes dont le sens a changé dans `bf7524b` exigent une décision éditoriale et une table de correspondance ; conserver l’historique sans attribuer arbitrairement une ancienne réussite à une nouvelle leçon.
5. **API publique versionnée par données, sans casser les routes.** Ajouter `GET /api/prep/manifest` avec `schemaVersion`, `generation`, hashes/révisions et retraits ; enrichir `/catalogue`, `/programmes/:code`, `/modules/:code` avec génération/révision et pagination des listes. Paramètre de révision pour rejouer une session commencée. `ETag/If-None-Match` et 304 ; métadonnées publiques cacheables, contenu protégé `private` et contrôlé avant même un 304. Ajouter les opérations admin sous `/api/admin/prep` : liste, création, détail, modification de brouillon avec révision attendue, validation, publication, archivage et suppression d’un brouillon non référencé. Réponse 409 sur édition concurrente, 422 sur graphe/contenu invalide.
6. **Étendre le panneau Web existant.** Onglet Préparation dans `Dashboard`, réutilisation des champs, boutons et styles admin. Édition Programme → Matière → Module → Leçon → Exercice ; aperçu dans les types supportés, validation des traductions et corrections, publication explicite. Un module partagé affiche ses programmes dépendants avant publication. Retrait = archivage et tombstone, pas suppression des historiques. Suppression définitive seulement pour un brouillon sans référence.
7. **Catalogue principal : cycle de vie explicite.** Ajouter `status` avec compatibilité des documents existants à `Organisme/Noeud/Matiere/ParcoursType`, routes PATCH/archivage sur les routes existantes, contrôle des descendants et références. Conserver les statuts de `Document` et ceux du catalogue historique. Le catalogue de découverte pourra présenter un organisme publié vide avec compteur 0 ; l’exploration des sujets conservera son filtre « au moins un sujet ». Ainsi, un organisme ne crée pas automatiquement une formation PREP. Réutiliser `/api/organismes` avec une projection publique publiée et pagination, sans exposer les données admin. Ajouter un compteur de révision du catalogue, incrémenté pour les mutations affectant les listes.
8. **Cache client commun dans son comportement, adapté à chaque plateforme.** Le manifeste est revalidé au démarrage, au premier plan, au retour réseau et toutes les cinq minutes pendant l’activité ; requêtes simultanées regroupées et temporisation après échec. Afficher le dernier snapshot valide immédiatement. Télécharger seulement le programme choisi et les modules ouverts/préchargés, stockés par code/révision/langue ; promotion du snapshot après validation complète. Ne jamais effacer la dernière copie valide après une panne ou un JSON invalide. Purger les retraits à la prochaine synchronisation, respecter un plafond de cache avec éviction des contenus non utilisés ; ne pas évincer les révisions référencées par une file non synchronisée. Brancher les accesseurs existants sur cet état réactif ; éviter une simple variable mutable qui ne ferait pas rerendre les écrans.
9. **Hors ligne : choix explicite sur les corrections.** Retenir des modules téléchargés sans correction des exercices notés : réponses et brouillons restent possibles hors ligne, résultat indiqué « En attente de synchronisation », correction et score définitif calculés au serveur. Les mini-questions pédagogiques non notées peuvent conserver leur correction locale, clairement distinguées. Ne pas déplacer tel quel le pack complet vers une API publique. Cela change la correction immédiate actuelle hors connexion, mais évite de prétendre cacher une clé livrée au client. Les réponses anciennes sont corrigées contre leur révision d’origine conservée ; aucune requalification silencieuse contre le nouvel énoncé.

Contrat admin à implémenter dans le lot 3 : `GET/POST /api/admin/prep/contenus`, `GET/PATCH /api/admin/prep/contenus/:kind/:code`, `POST /api/admin/prep/contenus/:kind/:code/valider`, `POST /api/admin/prep/publications` (liste des révisions et génération attendue), `POST /api/admin/prep/contenus/:kind/:code/archiver`, `DELETE /api/admin/prep/contenus/:kind/:code/brouillon`. `kind` accepte seulement `programme` ou `module`, les codes sont validés et immuables. La publication groupe les changements liés, y compris l’ajout d’un module dans un programme. Les index de leçons/exercices sont reconstruits et leur unicité globale validée avant activation.

Le passage disque → Mongo exige un chargement asynchrone explicite du snapshot avant traitement de la requête. Garder ensuite les recherches par code sur ce snapshot figé ; ne pas faire dépendre une notation en cours d’une mutation du cache global. Adapter aussi les consommateurs `progressService`, `rankingService` et les scripts vidéo ; une simple substitution de `readFileSync` par une Promise casserait leurs appels synchrones actuels.

### Apple : ne pas transposer automatiquement l’exception Google

Apple 3.1.1 impose normalement l’achat intégré pour débloquer contenu/fonctions numériques. 3.1.3(a) permet la consommation de médias achetés ailleurs pour les « reader apps ». 3.1.3(b), services multiplateformes, conditionne généralement l’accès aux acquisitions externes à leur disponibilité également en achat intégré. La vente individuelle de cours ne devient pas une vente institutionnelle 3.1.3(c), ni du tutorat individuel en temps réel 3.1.3(d). L’exception des compagnons Web gratuits 3.1.3(f) ne constitue pas une exemption générale pour toute app éducative. Les permissions particulières de la boutique américaine ne s’étendent pas à la boutique ivoirienne. [App Review Guidelines, 3.1.1 et 3.1.3](https://developer.apple.com/app-store/review/guidelines/#in-app-purchase).

Pour Apple, les médias (livres, audio, vidéo, etc.) doivent constituer la fonction principale du reader ; proposer quelques vidéos ne suffit pas. Le lien de compte externe demande une éligibilité et un entitlement spécifiques hors exceptions territoriales. [Critères officiels des reader apps](https://developer.apple.com/support/reader-apps/).

**Conclusion pour Fatafalta :** ses exercices interactifs, évaluations et fonctionnalités PREP empêchent de présumer cette qualification. Retenir immédiatement une UI sans achat, mais **ne pas annoncer l’iOS conforme ou publiable sur cette seule base**. Faire valider la qualification exacte par App Review ; si elle n’est pas acceptée, la contrainte « tout paiement sur le Web » implique de différer cette distribution iOS ou de réviser le périmètre commercial. Aucune IAP ou activation régionale dissimulée n’est proposée dans ces lots.

### Conception des droits et limites fournisseur

Étendre `Subscription` avec `accessState=enabled|suspended|revoked`, date/motif administratif et version de droits, tout en conservant le calcul de période. Valeur initiale `enabled` pour l’existant ; expiration toujours dérivée du temps. L’API publique distingue paiement en attente, abonnement actif/expiré et suspension/révocation. L’annulation d’une tentative ne retire pas une période déjà payée. Une résiliation commerciale éventuelle est distincte de la révocation immédiate : sans prélèvement automatique existant, ne pas inventer un endpoint « annuler chez GeniusPay ».

Toutes les autorisations (sujets, PREP, correction, téléchargement) passent par la même évaluation serveur tenant compte aussi du compte suspendu. `GET /api/me/entitlements` fournit `serverTime`, `checkedAt`, `validUntil`, `accessState`, capacités et version ; `/api/prep/droits` dérive ce même résultat avec l’essai PREP. Cache privé, aucune confiance dans une date ou un booléen envoyé par le client.

Pour le hors-ligne, retenir une autorisation de lecture locale bornée, délivrée par le serveur, au plus 24 h et jamais après la fin de période ; pour l’essai, au plus la fin du jour autorisé. Après échéance, nouvelle validation requise pour continuer le contenu protégé ; la file de réponses déjà enregistrées reste conservée. C’est une tolérance produit à documenter, pas une révocation instantanée hors connexion. Aucun mécanisme ne peut effacer un PDF déjà téléchargé ou garantir le secret d’un contenu livré à un client compromis.

Durcir la récupération des webhooks interrompus (état de traitement, bail/reprise), inclure `SUCCEEDED` non exécutés dans la réconciliation, refuser une confirmation dont les champs indispensables manquent. **Points fournisseur ouverts :** contrat exact de sérialisation de signature, caractère stable de l’identifiant de livraison, politique de relivraison, disponibilité des champs devise/métadonnées et sens des remboursements/contestations. Les fake providers testent l’intégration locale ; ils ne certifient pas ces fonctionnalités réelles. Toute validation fournisseur ultérieure devra suivre un lot explicitement autorisé, sans appel payant dans cette mission d’audit.

## C. Identité Web/mobile et synchronisation du compte

### Existant et écarts

- Les deux clients utilisent les mêmes `/api/auth/register`, `/login`, `/me` et le modèle `User` : `backend/routes/auth.js:25`. Aucun second compte requis pour acheter sur le site.
- Le serveur émet access et refresh JWT, cookie HttpOnly, puis renvoie aussi les jetons dans la réponse (`backend/controllers/authController.js:17`). Durées par défaut de 30 jours pour les deux (`backend/models/User.js:83`, `:89`). Refresh sans session révocable persistée ; logout efface seulement le cookie (`authController.js:117–155`).
- Mobile : access JWT dans SecureStore, refresh renvoyé mais non sauvegardé ; n’importe quelle erreur de bootstrap `/me`, réseau compris, supprime la session (`fatafalta/src/context/AuthContext.js:18–36`). Aucun intercepteur de renouvellement dans `src/services/api.js:44`. Le helper inutilisé `src/services/auth.js:61` vise `/api/auth/refresh`, alors que la vraie route est `/refresh-token`.
- Web : access JWT en localStorage et en Authorization, pas de cycle refresh, logout local seulement (`frontend/src/context/AuthContext.js:6`, `:22`, `:79`). Les jetons de session sont indépendants, mais il n’existe pas de gestion serveur par appareil permettant rotation/révocation.

PREP utilise une autre identité, `X-Prep-Token` HMAC, sans expiration (`backend/services/prep/identityService.js:14–26`). Ces identités ont des objectifs différents ; ne pas les remplacer par un unique jeton donnant tous les droits.
- Handoff : code aléatoire hashé, TTL deux minutes, consommation atomique avec `findOneAndDelete`, puis nouvelle session (`authController.js:158–189`, `models/AuthHandoff.js:10`). **Mais le code est un authentifiant temporaire placé dans la query string** par `useWebCheckout.js:24`; le Web le retire après lecture (`frontend/src/pages/SubscribePage.js:291`). Cela évite un JWT dans l’URL, mais ne satisfait pas la règle plus large « aucune information sensible dans l’URL » : historique, logs et referrer restent des vecteurs possibles avant retrait. Le parcours store supprimé n’en a plus besoin.
- Premier plan : pont `AppState → focusManager` existe (`fatafalta/App.js:94`), requêtes compte toujours relues au focus (`hooks/useAccount.js:14–34`), polling 5 s si PENDING. Une souscription Web devient donc visible sans reconnexion lorsque le mobile retrouve le focus et le réseau. Le Web vérifie son paiement auprès de l’API, pas via le paramètre de retour (`SubscribePage.js:123`, `:162`).
- Deux sources de droits divergent : `PrepBridge` injecte ACTIVE, mais `computeRights` fait un OU avec `droitsServeur.abonne` persisté sans date (`fatafalta/App.js:43`, `src/prep/store.js:320`). Une ancienne valeur vraie peut survivre à l’expiration ou à la déconnexion. L’app n’appelle pas périodiquement `prepApi.rights()` et `flush()` ne fait rien si la file est vide (`store.js:229`). Le hook Web des droits n’a pas de refresh au focus/retour visible (`frontend/src/hooks/useEntitlements.js:7`).
- **Propriété PREP à corriger avant la synchronisation :** `identityService.fromRequest()` ne compare pas le propriétaire au compte connecté (`:66`). Le rattachement peut assigner directement `identite.user=req.user._id` (`prepController.js:218`) ; les droits peuvent utiliser `identite.user` sans JWT (`progressService.js:28`). Un jeton PREP conservé après logout peut donc continuer à ouvrir les droits de l’ancien compte ; une identité déjà liée ne doit jamais être transférée à un autre compte. Risque établi par lecture, non exploité sur des données réelles.

### Conception retenue

Conserver `User` et les endpoints auth, introduire des sessions révocables `AuthSession` : identifiant de session, utilisateur, plateforme, hash du refresh courant, échéance, révocation. Index de session unique, index utilisateur et TTL d’expiration. JWT d’accès courts avec identifiant de session ; rotation du refresh et détection de rejeu. Web : refresh HttpOnly/Secure avec protections CSRF/origine, access en mémoire ; mobile : refresh SecureStore et renouvellement regroupé des requêtes concurrentes. Une panne réseau préserve la session locale ; un rejet authentique entraîne une sortie explicite. Nettoyer les logs d’erreurs Axios qui pourraient contenir les headers (`AuthContext.js:100`).

Au login, résoudre une identité PREP canonique appartenant au compte. Fusion invité → compte uniquement lorsque la preuve de possession est valable ; interdire compte A → compte B. Ajouter un index unique partiel sur l’utilisateur des identités canoniques après migration des doublons ; un JWT du propriétaire est obligatoire pour lire les données privées d’une identité liée. Le jeton invité ne doit pas conférer les droits Premium du compte. Namespace local par compte/identité, réinitialisation des droits, tokens PREP et caches privés à la déconnexion ; garder une file non envoyée dans son espace d’origine, jamais l’envoyer au nouveau compte.

Remplacer les booléens fusionnés par un snapshot de droits daté et unique. Après login, premier plan et retour réseau : rafraîchir droits puis progression, même file vide. Pendant l’activité, refresh des droits toutes les 60 s et à l’échéance connue ; PENDING conserve ses 5 s existantes. Dédupliquer les requêtes et arrêter les timers à l’arrière-plan. Le serveur refuse immédiatement une action interdite même si l’UI est en retard. Objectif de recette connecté : acquisition ou expiration propagée en un refresh au focus, ou en moins de 60 s en restant dans l’app. Aucun WebSocket nécessaire pour cette première version.

Le site `/abonnement` est utilisé avec sa propre connexion. Désactiver l’émission de handoffs commerciaux pour les builds stores et ne pas conserver de code bearer en URL. Si un passage interplateforme est ultérieurement indispensable, concevoir un appairage confirmé des deux côtés avec preuve échangée en POST ; l’identifiant de demande en URL ne doit, seul, jamais ouvrir une session.

## D. Continuité de l’apprentissage

### Existant vérifié

`PrepProgression` stocke l’état par `(identite, programme)` unique, scores et dernière activité (`backend/models/PrepProgression.js:9–26`). Le moteur partagé conserve leçons, meilleurs scores, modules validés, erreurs, révisions, blancs et minutes (`shared/prepCore.js:531`). `applyLesson()` préserve le terminé et borne la position ; les meilleurs scores sont monotones (`:595`, `:639`). `PrepTentative` conserve réponse et score serveur, session et clé client avec index unique partiel (`models/PrepTentative.js:4–24`). Son champ `version` reste au défaut 1 lors de l’ingestion : aucune révision de contenu effective transmise aujourd’hui.

Le client applique les réducteurs localement et persiste file, sessions et `enCours` (`fatafalta/src/prep/store.js:25`). Envoi après 1,5 s, paquets de 200 ; file tronquée aux 2 000 dernières actions (`:219–245`). L’état va dans un JSON global de l’app ou localStorage, écriture différée de 400 ms avec erreurs absorbées (`src/prep/storage.js:9–45`) ; le token PREP y est également conservé. Ce n’est ni une écriture atomique garantie, ni une partition par compte.

Le lecteur ouvre une leçon avec `terminee=false`, sauve au blur et la termine sur action explicite (`screens/ModuleLessonScreens.js:266–282`, `:328`). **Ouvrir n’équivaut donc pas à terminer : comportement à conserver.** Reprise du scroll par proportion (`:295`), mais `lastPos` prend le maximum atteint (`:315`) : revenir lire plus haut ne devient pas la dernière position. Les mouvements ne déclenchent pas de sauvegarde périodique ; une interruption brutale ou le passage en arrière-plan sans blur peut perdre le dernier passage. Les composants YouTube n’enregistrent pas de position de lecture dans `PrepProgression`.

Les sessions gardent localement question, réponses et état intermédiaire à chaque modification (`SessionScreen.js:294–318`). `enCours` et ces brouillons ne sont pas envoyés au serveur ; le test de positionnement est aussi local (`store.js:309`). La carte de reprise existe déjà : `PrepHomeScreen.js:248–258` pointe vers la leçon ou session locale, avec progression. L’améliorer plutôt que créer une seconde carte.

Le serveur recalcule les tentatives, sessions et blancs (`backend/services/prep/progressService.js:74`, `:122`, `:161`). Cependant :

- `flush()` retire toutes les actions du batch, même si `resultats` contient des refus individuels ; il ne réapplique pas systématiquement le reliquat sur l’état serveur (`store.js:233–240`).
- Seules les tentatives sont dédoublonnées. Rejouer `minutes` ou `blanc` double des compteurs ; le contrôle `exists` puis création n’est pas atomique avec la sauvegarde de progression (`progressService.js:125`, `:149`, `:175`, `:203`). Un crash entre tentative et état peut laisser une tentative enregistrée sans compteur appliqué.
- Plusieurs requêtes chargent puis sauvegardent le même état Mixed sans comparaison de révision ; il existe un risque d’écrasement entre appareils (`:42`, `:65`). Une leçon inconnue peut passer dans `applyLesson` ; appartenance exercice/module/programme et session doivent être validées. La lecture des tentatives d’une session ne filtre pas le programme/module (`:166`, `:177`).
- `/sync` ne renvoie que les programmes touchés par le batch ; pas de récupération privée complète au premier plan. `/appareils` renvoie un état lors de la déclaration, mais un appareil qui a déjà son token ne refait que `flush` (`store.js:138`).
- La fusion de rattachement additionne certains compteurs et donne priorité aux leçons de la cible, sans règle de date/position, sans migration complète des tentatives (`prepController.js:190–216`). Elle n’est pas une résolution générale de conflits.

**Web : aucun lecteur PREP, aucune carte de reprise ni exercice PREP** dans `frontend/src/App.js:101–126`. La version Expo Web éventuelle n’est pas le site React `frontend/`. Une continuité téléphone → ordinateur demande bien des pages dans ce dernier projet.

### Modèle et protocole retenus

Étendre `PrepProgression` plutôt que le remplacer : `revision`, `schemaVersion`, `etat.derniereReprise` (module, leçon/session, activité), état des leçons avec `lastPosition`, `maxPosition`, `videoPositionSec`, `contentRevision`, dates serveur ; état de session avec liste des codes/révisions, question courante, brouillons de réponses et statut. Borne de taille et nombre de sessions actives. Les anciens champs restent lisibles pendant la migration. Garder `terminee` monotone et les scores calculés par `prepCore` côté serveur.

Ajouter un journal `PrepAction` avec `(identite, actionId)` unique, programme, deviceId, séquence appareil, type, révision de contenu, payload borné, résultat et état d’application. La journalisation sert à reprendre un traitement interrompu et à dédoublonner **toutes** les actions ; elle ne devient pas un deuxième stockage de vérité de l’apprentissage. `PrepTentative` conserve le détail métier des réponses corrigées et référence l’action. Sans transaction Mongo, implémenter un traitement rejouable : réservation d’action, calcul déterministe, mise à jour CAS de la progression et marqueur d’application dans la même écriture, finalisation du journal ; reprise après chaque point de crash. Éviter toute addition non protégée. Ne pas supprimer les clés de déduplication tant qu’une file cliente peut encore les rejouer.

Contrat proposé :

- `GET /api/prep/progressions?cursor=…&limit=…` : états privés du compte/identité autorisée, révisions et curseur, aucune donnée d’un autre compte. Chargement complet initial puis changements ; un appel de lecture ne modifie pas `derniereActivite`.
- `POST /api/prep/sync` conservé et étendu : `deviceId`, version du protocole, révisions connues, actions identifiées ; chaque résultat est `applied`, `duplicate`, `rejected` définitif ou `retry`. Les champs legacy restent acceptés pendant une transition bornée.
- Actions additionnelles : reprise/leçon, brouillon de réponse, sauvegarde de session, résultat de positionnement. Le client ne soumet jamais un score faisant foi. L’état serveur contient les résultats des exercices et évaluations ; le serveur recalcule leur progression.

**Conflits :** succès de leçon = union logique, meilleure maîtrise = maximum des scores recalculés, tentatives/minutes/blancs = événements appliqués une seule fois. Dernière position et reprise = écriture conditionnelle sur révision ; une action hors ligne basée sur un état dépassé ne doit pas écraser une reprise plus récente d’un autre appareil. Le serveur retourne le conflit et son état, le client conserve la branche locale pour permettre « Reprendre sur cet appareil » et n’envoie un nouveau choix qu’après réconciliation. Horodatages clients bornés et utilisés comme information, jamais comme arbitre unique. Une séquence plus ancienne du même appareil ne remplace pas une séquence plus récente. Fusion invité → compte rejouable, scores/leçons fusionnés selon ces mêmes règles ; tentatives et clés d’idempotence réaffectées sans duplication.

**File et durabilité :** persister avant d’afficher une action comme sauvegardée ; écritures sérialisées, fichier temporaire puis remplacement et copie récupérable. Le token PREP quitte le JSON pour SecureStore. Supprimer uniquement les actions acquittées ou explicitement rejetées après conservation de leur diagnostic ; conserver les erreurs réseau et transitoires. Rebaser les actions restantes sur le snapshot serveur et relancer jusqu’à vidage, avec backoff. Supprimer le tronquage silencieux à 2 000 ; compacter les positions intermédiaires d’une même leçon, jamais les réponses ou soumissions. Afficher un état discret « Synchronisation en attente » et une erreur visible si le stockage est plein.

**Autosauvegarde et reprise :** position significative temporisée (par exemple 5 s ou changement de bloc), dernière réponse modifiée, changement de leçon, pause vidéo, blur et passage en arrière-plan. Écriture locale immédiatement déclenchée à l’arrière-plan ; envoi réseau au mieux, sans dépendre d’un traitement que l’OS peut interrompre. Reprise par identifiant de bloc et décalage, avec ratio de secours si la mise en page change ; le contenu demeure épinglé à sa révision pendant une session. La carte existante affiche formation, module, leçon, progression et « Reprendre » ; état découverte si aucun début. Une fermeture forcée peut survenir avant une écriture : ne pas promettre une garantie physique de zéro perte à chaque milliseconde ; borner la fenêtre et ne jamais déclarer acquittée une écriture échouée.

Pour le Web, réutiliser les API et `prepCore` (copie générée contrôlée comme sur mobile), `frontend/src/lib/api.js`, auth, `components/ui` et styles existants. Ajouter `/preparation`, `/preparation/:programme`, lecteurs et sessions, et la reprise dans `/compte`. Persistance Web des actions/brouillons et refresh sur visibilité/online selon le même protocole. Les composants React DOM sont adaptés ; aucune duplication du calcul des droits ou de la notation.

## Configuration, migrations et décisions avant publication

**Ce lot ne change aucune base ni API applicative.** Les seules écritures DB ont été les fixtures/nettoyages de la base locale de test. Le seul fichier livré est `docs/plateforme-dynamique/01-audit-conception.md` ; les notebooks et répertoires non suivis déjà présents sont laissés intacts.

Les lots futurs nécessitent les index et migrations décrits, une sélection explicite de base locale lors des essais, puis une procédure de migration de production séparément autorisée. Prévoir vérification à blanc des références, sauvegarde, compteur de publication, correspondances de codes, anciennes révisions et rollback. Les paramètres existants de paiement et les secrets restent côté serveur. `MOBILE_WEB_CHECKOUT=false` sera le défaut prudent, complété par l’interdiction native locale ; une variable seule ne corrige pas les anciens binaires déjà distribués.

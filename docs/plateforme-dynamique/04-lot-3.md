# Lot 3 — Publication du contenu et catalogue depuis l’administration

Implémentation du 13 novembre 2026, sur la branche courante, sans commit, push, déploiement ni accès à la production. Aucun fichier d’environnement ou d’identifiants consulté. Les paiements des tests utilisent exclusivement les fournisseurs factices existants.

## Comportement livré

Le dashboard propose maintenant **Préparation** et réactive **Institutions et structures**. L’administrateur peut créer et modifier des programmes/modules en JSON, sélectionner une matière, une leçon ou un exercice pour l’éditer séparément, consulter un aperçu textuel, valider, publier plusieurs révisions ensemble, archiver et restaurer une publication. Les corrections sont visibles dans cet espace réservé aux administrateurs. Les programmes dépendant d’un module partagé sont affichés avant publication. La pagination ne se limite plus aux cent premiers organismes.

Chaque sauvegarde PREP crée une révision, avec comparaison de la révision attendue. Le code du contenu est immuable. Une publication valide le graphe entier, les codes des leçons/exercices, les types de blocs pris en charge, les corrections acceptées par le moteur partagé et les traductions. Elle scelle les révisions puis active leur manifeste par une seule écriture conditionnelle MongoDB. Une interruption avant cette écriture conserve la publication précédente. Deux publications concurrentes n’ont qu’un gagnant ; le perdant reçoit 409. Les erreurs éditoriales renvoient 422 avec les détails.

Les requêtes publiques chargent explicitement leur snapshot Mongo et le conservent pendant tout leur traitement via AsyncLocalStorage. Les objets de contenu Mongo sont figés ; quatre générations au maximum restent en cache mémoire. Le registre est relu à chaque requête : une nouvelle publication apparaît sans redémarrage. Le calcul de progression et la migration de classement utilisent également un snapshot épinglé. `rankingService` lui-même lit seulement les scores enregistrés et n’a pas besoin d’un nouveau chargeur.

Le manifeste donne génération, schéma, révisions, hashes SHA-256 et retraits. Les réponses catalogue/programme/module conservent leur forme, avec des métadonnées supplémentaires. Les clés, explications et références de raisonnement des exercices notés ne sont pas envoyées par la lecture d’un module, y compris dans la version traduite. Les mini-questions pédagogiques non notées gardent leur correction, conformément à A.9. L’identité et les droits serveur sont vérifiés avant tout 304 du module protégé ; cache privé avec revalidation. Les métadonnées publiques utilisent également ETag/If-None-Match.

Une lecture `?revision=N` retrouve une révision effectivement publiée, même après retrait. Pour un ancien programme, les modules sont ceux du premier manifeste ayant publié cette révision du programme. Le manifeste courant reste la référence pour connaître les révisions des modules partagés à utiliser dans une nouvelle session. Le protocole d’actions hors ligne et la notation contre une ancienne révision restent au lot 5.

L’archivage PREP retire la référence du manifeste et émet un tombstone ; les révisions publiées et les progressions sont conservées. Le retrait d’un module encore référencé est refusé ; retirer les références des programmes dans la même publication permet un retrait groupé. La suppression d’un brouillon non référencé efface son payload, mais garde une trace de révision pour ne jamais réutiliser son numéro. Une révision scellée lors d’une publication interrompue ne peut plus être modifiée : créer une nouvelle révision ou republier celle-ci.

Les organismes, nœuds, matières et parcours ont un statut explicite. Les anciens enregistrements sans statut restent publiés. La découverte `/api/organismes` peut afficher un organisme vide avec compteur zéro ; `/api/catalog/organismes` conserve le filtre « au moins un sujet approuvé ». Les listes publiques filtrent les brouillons/archives ; `scope=admin` nécessite une authentification administrateur. Les références publiées et descendants empêchent l’archivage d’un parent. Les changements du catalogue, des structures et des documents incrémentent un compteur de révision partagé.

Les outils vidéo reçoivent un snapshot explicite depuis la connexion Mongo dédiée. Les nouveaux enregistrements portent révision et génération source. Une vidéo ancienne sans révision vérifiable, marquée à revalider ou liée à une autre révision, n’est pas associée au contenu Mongo servi. Aucune publication YouTube/Facebook/TikTok exécutée.

## Base de données et migration

| Collection | Champs/indexes |
| --- | --- |
| `prepcontents` | `kind`, `code`, `revision`, `schemaVersion=1`, `status`, `payload`, `hash`, `author`, dates. Index unique `(kind,code,revision)` ; index `(kind,status,updatedAt,_id)`. |
| `preppublications` | Un registre `_id=active` : génération, références, tombstones, auteur, dates et historique de manifestes. L’historique et l’activation sont atomiques dans le même document, sans replica set obligatoire. |
| `catalogrevisions` | Un registre `_id=catalog`, compteur `revision` et dates. |

Aucune collection de progression ou tentative supprimée, aucun identifiant pédagogique recréé. Pas de migration automatique au démarrage. Avant la première publication via HTTP, l’import explicite est obligatoire afin de ne pas remplacer accidentellement tout le catalogue historique par une seule nouvelle leçon.

Depuis `backend/` :

```sh
# Lecture seule, aucune lecture dotenv, base locale obligatoire.
node scripts/migrations/lot3.js --uri=mongodb://127.0.0.1:27017/fatafalta-dev

# Après résolution des correspondances, application locale explicite.
node scripts/migrations/lot3.js --uri=mongodb://127.0.0.1:27017/fatafalta-dev --links=/chemin/liaisons.json --apply
```

`liaisons.json` associe chaque code programme à `{ "organismeId": "ObjectId", "parcoursTypeId": "ObjectId" }`. Sans correspondance explicite, le script recherche un organisme non ambigu puis son parcours. Une correspondance absente ou ambiguë empêche l’application. Il n’invente pas d’organisme. Il importe 39 modules et 8 programmes, reprend des révisions identiques après interruption et refuse d’écraser une édition différente. Après une première activation, une relance conserve toutes les éditions et termine seulement les opérations additives éventuelles. Les index sont créés sans supprimer les anciens index.

Le contrôle à blanc sur `fatafalta-dev` a signalé les **8 programmes non rapprochés** ; aucune application effectuée sur cette base. Les imports appliqués et répétés ont été testés uniquement sur la base locale jetable `fatafalta-test`, avec des organismes/parcours de fixture. Le script refuse une URI distante. Une migration de production exige une procédure séparée et autorisée.

Rollback : sélectionner l’ancienne publication dans le panneau, ou envoyer `rollbackGeneration` et `expectedGeneration` à l’API. Cela crée une nouvelle génération portant les anciennes références, sans effacer les révisions ultérieures ni les apprentissages. Aucun retour automatique au pack après activation Mongo.

## Contrats HTTP

Préfixe `/api/admin/prep`, administrateur uniquement :

- `GET /contenus?page=&limit=&kind=&status=` : révisions paginées, génération, références actives, historique des générations ; indicateurs `active` et `withdrawn`.
- `POST /contenus` : `{kind,code,payload}` ; nouvelle révision 1.
- `GET /contenus/:kind/:code` : dernière révision et programmes dépendants.
- `PATCH /contenus/:kind/:code` : `{payload,expectedRevision}` ; ajoute la révision suivante ou 409.
- `POST /contenus/:kind/:code/valider` : `{revision}` facultatif ; validation dans le graphe courant.
- `POST /publications` : `{expectedGeneration,revisions:[{kind,code,revision}],removals:[{kind,code}]}` ; publication groupée. Alternative : `{expectedGeneration,rollbackGeneration}`.
- `POST /contenus/:kind/:code/archiver` : `{expectedGeneration}`.
- `DELETE /contenus/:kind/:code/brouillon` : `{expectedRevision}`.

Public : nouveau `GET /api/prep/manifest`. `/prep/catalogue` accepte `page/limit` (maximum 100 groupes) ; `/prep/programmes/:code` et `/prep/modules/:code` acceptent `revision`, avec `version` linguistique existant pour le module. Les champs de réponse existants restent présents. La lecture des vidéos suit la révision du contenu.

Catalogue : `PATCH /api/{organismes|noeuds|matieres}/:id`, `PATCH /api/parcoursTypes/:id` ; mêmes chemins suivis de `/archiver` en POST. Champs modifiables : `nom`, `description` quand applicable, `status`. Les routes de création existantes acceptent aussi le statut. Les listes exposent `meta.revision`, et les parcours ont une pagination additive.

## Configuration, limites et points ouverts

- Pas de secret ou nouvelle clé nécessaire. Les deux collections PREP doivent être importées avant utilisation de l’éditeur pour publier. Avant cet import uniquement, les lectures legacy restent compatibles avec le pack déjà distribué.
- `schemaVersion=1` accepte les types de blocs/exercices déjà rendus par l’app. L’éditeur est un éditeur JSON avec sélection hiérarchique et aperçu textuel, pas un éditeur visuel reproduisant exactement React Native. Le serveur reste l’autorité de validation.
- La limite JSON HTTP existante est `SEC_JSON_LIMIT` (200 ko par défaut), avec plafond éditorial de 2 Mio par payload. Les modules actuels passent sous 200 ko. Un contenu plus volumineux nécessite un réglage serveur explicite, sans jamais dépasser le plafond éditorial.
- Historique des manifestes conservé dans le registre atomique : surveiller sa taille avant d’approcher la limite MongoDB de 16 Mio. Aucun effacement automatique de l’historique n’est introduit.
- Les codes dont le sens a changé dans `bf7524b` restent une décision éditoriale : aucune correspondance pédagogique ni ancienne réussite réattribuée par cette migration. Les vidéos historiques sont à revalider. Les anciennes révisions antérieures au pack importé ne sont pas inventées.
- Les outils de publication vidéo exigent maintenant une publication Mongo et transmettent un snapshot. Le CLI de brief accepte `--uri` explicite et limité au local ; les fonctions réutilisables acceptent un snapshot de fixture. Aucun service vidéo distant validé par cette recette.
- Le compteur catalogue est un mécanisme d’invalidation, pas une transaction multi-collections. Une écriture applicative brute hors modèles doit prévoir son incrément. Les scripts de migration livrés sont locaux ; aucun script de maintenance production exécuté.
- Le chargement dynamique mobile, le cache hors ligne et la purge des retraits restent au lot 4 ; la synchronisation des anciennes réponses/révisions et la reprise au lot 5 ; le lecteur Web au lot 6. La lecture API immédiate est testée, pas une mise à jour du bundle mobile existant.
- Ni paiement, ni règle de renouvellement A/B, ni qualification iOS modifiés. Les réserves fournisseur/store des lots précédents restent ouvertes. Référence SDK demandée consultée : [Expo SDK 56](https://docs.expo.dev/versions/v56.0.0/), sans changement d’API native dans ce lot.
